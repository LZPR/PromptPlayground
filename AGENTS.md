# Repository Guidelines

## Project Structure & Module Organization

This repository contains product and implementation specifications under `doc/`:

- `doc/spec/` contains the feature contracts for sessions, chat UI, messages, branches, generation, and architecture.
- `doc/spec/tests/` contains data-structure test specifications and shared fixtures/invariants.
- `doc/idea.md` contains early product notes.

The application scaffold is split by runtime:

- `frontend/` contains the Vue 3, TypeScript, Pinia and Vue Router application.
- `frontend/src/domain/` contains pure domain types and message-tree transformations.
- `frontend/src/repositories/` contains frontend persistence contracts; components and stores must not issue SQL.
- `src-tauri/` contains the Tauri 2 application, Rust commands, repository contracts, migrations, model networking and secret storage.
- `src-tauri/gen/android/` is generated by Tauri and ignored by Git; regenerate it with the Android initialization command when needed.
- `e2e/` contains Playwright browser smoke and workflow tests.

Keep Vue/TypeScript UI and Pinia state in the frontend, Rust/Tauri commands and migrations in the backend, and route persistence through the three repository abstractions; do not scatter SQL through components.

## Build, Test, and Development Commands

Install JavaScript dependencies once with `npm install`. The project uses the local `@tauri-apps/cli`; do not rely on a globally installed Tauri CLI.

- `npm run dev` starts the browser frontend on `http://127.0.0.1:1420`.
- `npm run build` type-checks the frontend and creates `frontend/dist`.
- `npm run lint` checks TypeScript, Vue and configuration files.
- `npm run test` runs Vitest domain/store tests.
- `npm run test:e2e` runs Playwright tests. On a new machine, install Chromium first with `npx playwright install chromium`.
- `npm run tauri:dev` starts the Windows desktop application.
- `npm run tauri:build` creates the Windows release bundle. For a fast compile-only check, run `npm run tauri -- build --debug --no-bundle`.
- `npm run android:init` generates `src-tauri/gen/android`; run it after cloning or when Tauri Android configuration changes.
- `npm run android:dev` deploys to a connected Android device or emulator, and `npm run android:build` creates an Android build.
- `cargo test --manifest-path src-tauri/Cargo.toml` runs Rust unit tests. The project pins the stable MSVC toolchain and Android targets in `rust-toolchain.toml`.

Required local tools are Node.js 22+, Rust stable/MSVC, Visual Studio 2022 C++ Build Tools and WebView2 for Windows. Android development additionally requires JDK 17, `ANDROID_HOME`, Android Command-line Tools, SDK Platform/Build Tools, NDK `30.0.15729638`, and the four targets declared in `rust-toolchain.toml`.

On this workstation, `rustup` may fail with an access-denied error for `C:\Users\CJL\.cargo\bin\rustup-init.exe` after self-update. Repair the user-level Rustup installation before relying on normal `cargo` or Tauri commands; the project itself must not encode machine-specific toolchain paths as a workaround.

## Coding Style & Naming Conventions

Use the planned stack: Vue 3, TypeScript, Vite, Pinia, and Tauri 2 with Rust commands. Follow the formatter and linter configuration introduced with the app scaffold; use two-space indentation for TypeScript/Vue and standard `rustfmt` formatting for Rust. Name Vue components in PascalCase, composables with `use...`, stores by domain, Rust functions/modules in `snake_case`, and repositories/services in PascalCase. Keep persisted message text unchanged between Raw and Markdown display modes.

## Testing Guidelines

Use Vitest for domain logic, Pinia, repository mappings, and settings persistence; Rust unit tests for SSE parsing, cancellation, timeouts, and error mapping; and Playwright for end-to-end workflows and responsive layouts. Follow the specs' Given/When/Then style and names such as `[branch] delete [preserves tree invariants]`. Use static IDs and fixed `createdOrder`; avoid random or time-dependent fixtures. Assert complete state for accepted and rejected operations, including that rejected operations do not mutate inputs.

## Commit & Pull Request Guidelines

The repository currently starts with `Initial project commit`; no longer-term convention is established yet. Use short, imperative subjects (for example, `Add message tree domain model`) and keep each commit focused on one logical change. Before committing, review `git status` and the staged diff. Pull requests should explain the behavior changed, link the relevant specification or issue, describe tests run, and include screenshots for UI changes. Keep specifications synchronized with implementation and call out migration or platform impacts.

## Security & Configuration

API keys are prototype-local configuration only. Access them through the `SecretStore` abstraction, never hard-code or log them, and keep model requests in the Rust network layer. Use parameterized SQL and transactional, uniquely versioned SQLite migrations.
